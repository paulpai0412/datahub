First-party DataHub extension

用 Composer 把 ETL 關係安全地匯入 DataHub

使用者只需在同一個 DataHub Agent 聊天提供已授權的工作區與入口；系統會分析 DataFlow、DataJob、表／欄位 lineage，展示差異，等待可信的人類確認後才寫入 DataHub。

入口：datahub_etl 目前 UI：DataHub → Agent → Chat 完成後：原生讀回／reload

目前可操作的流程

這是一條「metadata import」流程：分析程式碼與既有 Catalog，不會因為匯入而執行來源 ETL。

使用者實際操作

一般使用者不需要輸入 Task／Run／Agent URN，也不需要撰寫腳本。

開啟 Agent Composer

進入 DataHub → Agent → Chat。使用目前登入的 DataHub 身分；不要直接把 gateway port 當成使用者入口。

指定已授權工作區與入口

提供工作區目錄、workspace 相對的 Python 路徑，以及入口函式。路徑必須落在已授權 workspace 內。 

請用 datahub_etl 分析 /home/timmypai/apps/datahub/extensions/sales-datamart 的 src/sales_datamart/etl.py，入口 run_etl。只做 metadata 靜態分析，顯示完整 Flow／Jobs／table／field lineage 與差異，最後等待可信人工確認。

處理必要的連線歧義

若畫面要求選擇 source／target connection，選擇已核准的 DataHub Source。不要用資料庫名稱自行猜 URN；選項應由 Host 讀回。

閱讀預覽，不要急著核准

檢查 Flow／Jobs、輸入輸出、欄位來源、條件、生成欄位、完整性分母、source gaps，以及新增／不變／衝突差異。看到 blocker 時先處理 blocker。

在可信 review 對話框確認

確認內容與 plan digest 後，將白色 review 對話框捲到底，按 Approve and import lineage metadata。這個按鈕才會觸發發布；聊天文字或一般同意不取代它。

等待讀回完成

匯入後看卡片上的 native readback 狀態。完成標誌是 VERIFIED_CURRENT_VALUES，並且每個觀測項目都是 MATCHED。之後可重新開啟聊天或 reload 頁面確認不重播。

系統自動處理

Host 會自動取得 snapshot、Catalog schema、來源 scope，建立 native Task／Run／Decision，並由 compiler 產生 DataFlow／DataJob／lineage 差異。模型只提供分析意圖，不提供可直接寫入的 Aspect。

預覽卡片要看什麼

預覽是核准前的決策材料；它不等於已發布，也不等於 ETL 已執行。

F

DataFlow

顯示穩定的 pipeline 身分、實際入口與來源快照。不是把工作區每個檔案都當成一條 Flow。

J

DataJobs

顯示真正的處理步驟、輸入／輸出與相依關係。helper 不會被不加判斷地當成 Job。

↔

表與欄位 lineage

顯示 source／target Dataset、欄位來源、條件、生成欄位與證據位置；不支援或未解析項目仍會保留。

Δ

Native diff

區分新增、更新、不變與衝突。既有 ownership、tags、terms、描述及無關 lineage 不應被默默覆蓋。

!

完整性與 blocker

完整性有明確分母。source gap、schema 歧義、workspace 越界或缺少回讀時，不應顯示為 COMPLETE。

✓

Published readback

發布後顯示實際 native 值與 provenance。只有讀回一致，才算這次匯入閉環完成。

狀態 意思 使用者動作
PREVIEW 仍在分析或等待必要 scope／connection 選擇。 閱讀 blocker，補做允許的選擇；不要把預覽當已發布。
AWAITING_HUMAN 已建立可信 review，尚未取得人工核准。 檢查白色對話框內容後，按指定的 Approve 或 Reject。
VERIFIED_CURRENT_VALUES 一次性發布成功，Host 讀回的值與計畫一致。 確認每項為 MATCHED，再做 readback／reload；不要重送。
ERROR / UNKNOWN 拒絕、部分寫入、過期或結果不明。 停止重試，先讀回 Task／Run／Decision 與 native 狀態。

常見情況與處理方式

失敗紀錄會保留；不要用新一次 import 覆蓋不確定的舊結果。

看到「Approve」按鈕在哪裡？
在白色的 Lineage publication review 對話框內向下捲動。按鈕通常位於底部，右側是 Approve and import lineage metadata，旁邊可能有 Reject。不要按聊天輸入區的 Stop 代替核准。
模型把 pythonPath 傳成絕對路徑
這會被 workspace 邊界拒絕。改用工作區相對路徑，例如 src/sales_datamart/etl.py，並在同一 session 續作；確認前一輪沒有 Task／lineage 寫入。
頁面 reload 後圖卡似乎不見了
先展開對應的 Process details。圖卡資料保存在聊天訊息；收合的 process details 不代表資料遺失。若發布已完成，優先使用 read_import 唯讀對帳。
匯入後可以再按一次嗎？
不可以。每個 publication attempt 是一次性消耗的。已成功、部分寫入或不明結果都先 reconcile／readback，不自動 replay。
這個流程會執行 SQL 或 ETL 嗎？
不會。Composer 匯入是 metadata 靜態分析與 DataHub metadata publication；它不 import／execute repo code，不跑業務 SQL，不做 DDL／DML，也不安裝 repo dependencies。
我想加入另一個工作區
路徑本身不是授權。必須先由可信 Host 明確核准 workspace root、Source／Dataset scope 與必要的 Catalog 可見權限，再開始分析。

功能邊界與安全原則

這些界線是流程的一部分，不是可在 prompt 中繞過的選項。

不會做的事

  • 不執行 ETL、SQL、DDL、DML 或來源程式。
  • 不讀取或輸出來源憑證。
  • 不建立新 service、datastore 或通用 executor。
  • 不修改 DataHub Core。

發布前的保護

  • 檢查 actor、workspace、Source scope、schema／版本與 plan digest。
  • 由 Host 產生 native Aspects，不接受模型直接塞入的寫入內容。
  • 使用 CAS／ownership／ACL 與一次性 attempt。
  • 可信父對話框是必要的人工授權邊界。

結果如何解讀

  • MATCHED 證明 native metadata 與本次計畫一致。
  • 不等於業務關係正確或 ETL 執行成功。
  • 靜態欄位完整性不等於 runtime／business semantics 完整。
  • 未解析 source gaps 會保留在證據中。
