## 原生稽核隔離可行性：固定 Core 的唯讀檢查

使用者已明確選擇 **S4 審核必須原生隔離**；本輪不新增敏感 S4 審核寫入，也不改現行 All Users 政策。這項結論不回溯刪除 S3 已存紀錄，其目前的 `EXISTING_TASK_RUN_ACL` 可見性依上述真收據保持如實標示。

- 固定版 `metadata-service/auth-impl/.../PolicyEngine.java` 的 `getGrantedPrivileges` 把所有適用政策的 privilege 作聯集；沒有可覆蓋既存 All Users `VIEW_ENTITY_PAGE` 的 deny 規則。`isResourceMatch` 對無 resource filter 的 metadata policy 直接返回 true。**另加一條 scoped policy 不能讓已可讀的非 owner 變不可讀**；首先須處理既有全域 grant，影響不止 Agent。
- 該引擎可比對 TYPE、URN、OWNER 等欄位，條件支援 `EQUALS`、`STARTS_WITH`、`NOT_EQUALS`，但沒有 `NOT_STARTS_WITH`。`NOT_EQUALS` 對缺失欄位會通過，不能當安全的「除 Agent URN 前綴外全部可見」規則。資源 owner 規則讀 **原生 `ownership` Aspect**，不讀自訂 `ekopAgentRun.actor`；固定 `entity-registry.yml` 的 `dataJob` 支援 ownership，`dataProcessInstance` **未列 ownership**。因此不能只用新建 owner policy 讓既有 Semantic Run 自動按自訂 Actor 私有。
- 若把 All Users 改為排除 `DATA_JOB`／`DATA_PROCESS_INSTANCE` 再重建讀權，非 Agent 的 DataFlow Jobs、原生 execution runs 及既有 Catalog 讀者都可能受影響；按 URN 列出現存 Agent 紀錄不能覆蓋未來的 Run，按固定平台白名單重建可見性也不是可升級的通用解。`upsertPolicy` 的公開 GraphQL `PolicyUpdateInput` 無 expectedVersion，固定 resolver 用普通 MCP ingest 並自行 invalidates cache；目前沒有已證實的政策 CAS／原子切換或可安全自動回滾契約。
- 下一安全門檻：已私下封存一次完整原生 Policy 值／版本及三個資產的 B 權限觀測，但尚欠其他 Actor／Catalog 範圍、歷史資料 owner、並發版本／cache／事件收斂與回復演練。僅在隔離測試部署做有界政策負例：非 owner 原生 batchGet 與 Host get_run 必須拒絕，owner 可讀，既有 Catalog 仍按原生值可見；失敗先對帳，不重播或自動回滾。若固定版無法同時滿足，先提出官方 Model／Policy 擴充或獨立 SSO Workbench 的明確取捨；不補 Core、不另建 datastore、不以 Host owner guard 冒充原生 ACL。正式政策切換另需對目標與操作的明確批准。
